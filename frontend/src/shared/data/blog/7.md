# Specifications before code.

Today is focused on **Spec-Driven Development** and how specifications can be used when working with AI coding agents.

The idea is pretty simple. Before asking an agent to build something, I should describe what I actually want. Not just write a vague prompt and hope the agent understands the same thing I do.

I started by looking at how a feature can be broken down into requirements, flows, tasks and acceptance criteria. This is something I already do to some degree when I work on my own projects, but I normally keep most of it in my head or in a quick Github issue. That is probably not enough when another developer or an agent needs to understand the work.

### The specification is the source of truth

A good specification should explain the goal, the scope and what is not part of the task. It should also explain how the result can be tested. If I only tell an agent to “make a customer search”, it can make a lot of assumptions about the endpoint, the response, the files it may change and what should happen when no customer is found.

If I instead describe the expected request, response, allowed files, technical restrictions and tests, the agent has something concrete to work from. It does not remove the need for me to think, but it makes the thinking visible and easier to review.

I especially like the idea of including stop conditions. If an agent discovers that a database migration is needed or that it must change a public API, it should stop and ask instead of making a decision on its own. That is a much better safety net than hoping it will make the same architectural choice as me.

### Peter Naur and programming as theory building

We also worked with Peter Naur's idea of **programming as theory building**. The important point for me is that programming is not only about producing code. The developer builds an understanding of the problem, the domain and the system, and the code is an expression of that understanding.

This is also where I see a problem with relying too heavily on agents. An agent can produce a working implementation without actually sharing my theory of the system. It can follow patterns and pass tests, but still make a choice that does not fit the architecture or the business problem.

That means a specification is not just a prompt for an agent. It is a way for me to put my understanding into a form that can be challenged, reviewed and used by someone else.

### How I will use specs

Going forward, I want to use a small specification before I ask an agent to implement a feature. It should contain the goal, the allowed scope, acceptance criteria, verification steps and stop conditions. For larger changes I will also include the expected data flow and the architectural boundaries.

I still want to be the person who makes the decisions. The agent can help with implementation, searching and repetitive work, but the specification should come from my understanding of the problem.

That is my main takeaway today. AI-driven development does not make clear thinking less important. It makes clear thinking even more important.
