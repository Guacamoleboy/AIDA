# Specifications before code

Today focused on **Spec-Driven Development** and how specifications can support work with AI coding agents.

The main lesson is that a prompt is not enough for a larger project. Before an agent implements anything, I need to describe the problem, the domain, the intended user flow and the boundaries of the work.

### The specification is the source of truth

A useful specification explains the goal, target users, scope, non-goals, user flow, functional requirements, acceptance criteria and testable boundaries. It should make the important decisions visible instead of leaving them in my head.

For the Engestofte Gods project, this means documenting the customer journey from `/kontakt` through the AI-flow, login/register, `/dashboard/events/` and the approved event under `/dashboard/events/{id}`. It also means defining the difference between customer data, Owner information, Staff read-only information and AI suggestions.

### Small vertical tickets

The work should be divided into small tickets that can each be demonstrated. A ticket should not simply be “build the frontend” or “create the backend”. It should deliver a complete user-visible slice, such as one working AI interaction, one complete flow step or one approval transition.

Each ticket should include its scope, out-of-scope rules, acceptance criteria, verification method and stop conditions. This gives the agent a clear contract and makes it easier for me to review the result.

### Peter Naur and programming as theory building

Peter Naur’s idea of programming as theory building is especially relevant to AI-assisted development. An agent can produce code without sharing my understanding of the business problem. The code may look reasonable while still being wrong for the domain.

The grilling session, glossary, decisions, system sketch, specification and tickets are therefore not just administration. They are how I build and preserve the theory of the Engestofte solution.

In a study environment I expect a bit more from the teaching material and the preparation of the exercises.

I do not think refusing one exercise means that I should ignore the subject. ### How I will use specs

I will use a short specification before asking an agent to implement a feature. For larger changes, I will also maintain a domain glossary, record important architectural decisions and split the work into dependency-aware tickets.

The agent can help me search, explain and implement. I remain responsible for the problem definition, the boundaries and the final review. AI-driven development does not make clear thinking less important. It makes clear thinking more important.
