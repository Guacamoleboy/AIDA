# Finishing the project and preparing for the exam

The project work is now moving from implementation towards a clear demo and explanation. The AIDA course describes this stage as finishing the project, documenting it and preparing a demo; the following session is for the demo and exam preparation. ([AIDA project session](https://aida.kursusmaterialer.dk/15-projekt/); [AIDA demo and exam preparation](https://aida.kursusmaterialer.dk/16-projektdemo-eksamensforberedelse/))

### What I built

The project starts with the problem of collecting wedding enquiries with many details and follow-up questions. The customer can use a guided AI-flow, save a draft, submit it after login or registration, and have the enquiry reviewed by the Owner. The broader product gives the customer and Engestofte a shared place for event information and later communication.

The AI-flow combines fixed application questions with AI-generated acknowledgements and follow-up questions. After each answer, the backend sends the system instructions and a user prompt containing the current request, conversation and rubric to OpenAI. OpenAI returns structured JSON; the application uses it to update the current draft and decide what the customer sees next. The local [prompt-flow diagram](../docs/diagrammer/ai-prompt-flow.svg) and [draft-structure diagram](../docs/diagrammer/ai-structure.svg) make those responsibilities easier to explain.

### What remains a prototype decision

The AI does not check a live wedding calendar, confirm prices or make a booking. Those facts require an authoritative business source and Owner confirmation. MCP could later expose a narrowly scoped date-availability tool, but no MCP integration is currently implemented.

The prototype also stores its unfinished draft in browser `localStorage` and sends conversation data to an external AI provider. That is useful for demonstrating the flow, but it is not a production privacy approval. Before real deployment, data handling, retention, access control, provider terms and AI transparency would need a dedicated review.

### How I am preparing to explain it

For the demo, I want to show one complete path rather than every screen: start an enquiry, answer a few questions, show how the draft fills in, then submit it for Owner review. I will explain the project decisions behind that path:

1. **Why this problem:** wedding information is detailed, and Johan needs a clear enquiry to review.
2. **Where AI helps:** interpreting natural-language answers, asking relevant follow-ups and producing structured output.
3. **Where the application stays in control:** fixed step questions, draft state, step transitions, validation and access control.
4. **Where the human stays in control:** real availability, prices, approval and booking.
5. **What I would improve next:** privacy review for production and, if a trusted calendar becomes available, a read-only MCP date-check tool.

I also need to be able to explain the difference between a system prompt, a user prompt and a rubric; how the same draft structure is filled over time; and why a valid structured response still needs validation and human review. These are decisions I can point to in the code and project documentation, not just features I can describe abstractly.

### Final thoughts

The most useful result is not simply that the application can call an AI model. The project now connects a real business problem to a defined customer journey, an implementation and visible limits on what AI may decide. My exam preparation is to demonstrate that journey and explain why each responsibility belongs where it does.
