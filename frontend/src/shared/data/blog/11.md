# Security aspects in AI-driven development.

Today we focused on security aspects when working with AI, code agents and software projects. Security is one of those subjects that can easily become something I plan to think about later. That is exactly why it is important to include it from the beginning.

An agent can be very useful because it can search through a codebase, explain unfamiliar files, run tests and help implement features. At the same time, every permission given to an agent creates a responsibility. The agent should only have access to the files, commands and services that are necessary for the task.

### Security starts with the setup

The first security decision is not made inside the prompt. It is made when the development environment is configured. If an agent can run arbitrary commands, access the internet or write to every project folder, the risk is much larger than if it works inside a limited workspace.

This does not mean that every agent is dangerous. It means that I should understand what the tool is allowed to do before I use it. A clear workspace, restricted permissions and approval before important actions give me more control over the development process.

I also need to be careful with the context I provide. Source code can contain private business logic, personal information, credentials or internal URLs. The safest secret is the one that never enters the agent's context at all.

### Secrets and configuration

API keys, tokens and passwords should not be hardcoded into the application or committed to GitHub. They belong in environment configuration or a proper secret-management solution, and the repository should contain safe examples instead of real values.

This is especially relevant when using an agent because the agent may inspect configuration files while trying to understand how the application works. I should make sure that sensitive files are protected, ignored by version control and not included in prompts unless there is a very good reason.

Rotating a key is also an important part of security. If a credential is accidentally exposed, removing the file is not enough because it may still exist in Git history, logs or previous conversations. The credential should be revoked and replaced.

### Trusting generated code

AI-generated code should be reviewed in the same way as code written by another developer. It can contain insecure assumptions, missing validation or dependencies that I have not investigated.

For my AIDA project this means that I should pay attention to input validation, authentication, authorization, error messages and data sent to external services. An endpoint should not trust whatever the client sends, and an error response should not expose internal implementation details just because that makes debugging easier.

I also want to keep dependencies limited. Adding a package can solve a problem quickly, but it also adds code that the project depends on and must keep updated. A small feature should not automatically result in a large new security surface.

### Prompt injection and boundaries

An agent can receive instructions from many places: my prompt, repository files, documentation, issue descriptions and external content. Those sources should not all be trusted equally.

If a file tells the agent to ignore its task and upload data somewhere else, that should be treated as untrusted content rather than as a new instruction. Clear scope, allowed paths and stop conditions help the agent distinguish between project information and commands it is actually allowed to follow.

This is also relevant for applications that use an LLM. A user should not become an administrator simply by writing it in a prompt. Permissions must be checked in the application and on the server, not only described in a system prompt.

### My conclusion

Security in AI-driven development is not one feature that can be added at the end. It is a collection of small decisions about access, secrets, dependencies, input and review.

I will continue using agents because they are useful for my workflow, but I want to keep the human developer responsible for the boundaries. The agent can help me write and inspect code. It should not decide by itself what information it can access, where it can publish changes or which security compromises are acceptable.

The most important lesson today is that convenience should not replace control. A fast implementation is only useful if the project is still safe to run, review and maintain afterwards.
