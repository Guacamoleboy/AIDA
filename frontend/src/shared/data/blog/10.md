# Working with agents in my project

Today focused on **Collaborative Agentic Development**. I work alone on my AIDA project, so collaboration means creating a reliable process between myself and the AI agents I use.

### The project needs shared context

An agent should not have to rediscover the entire project in every session. I now keep the important context in a small set of documents: the project description, grilling decisions, flow definition, domain glossary, system sketch, specification and implementation tickets.

The documents have different purposes. The glossary defines the meaning of terms such as `Owner`, `Staff`, `forespørgsel`, `event-platform` and `ændringsforslag`. The specification describes the agreed solution. The tickets describe the next small piece of work.

### Tickets as contracts

A useful ticket does more than say “build this feature”. It explains what the customer or Owner should be able to do, what is in scope, what must not change, how the result can be verified and when the agent must stop and ask.

For example, the Engestofte project does not have one large ticket called “build the AI system”. It has smaller vertical slices: establish the application shell, prove one OpenAI interaction, complete the five-step enquiry, persist the request, let Owner review it and then add the event platform.

This makes the work easier to review and reduces the risk of an agent implementing several unverified assumptions at once.

### Agent boundaries and ownership

The agent may search the repository, explain existing code and implement the approved ticket. It should not perform unrelated refactoring, change public contracts without permission or continue when the specification and the codebase disagree.

I remain responsible for the domain decisions, the allowed scope and the final review. The agent can suggest a solution, but it cannot decide whether the customer should receive a binding price, whether an event is bookable or whether sensitive information may be exposed.

### My workflow

My workflow is now:

1. Clarify the problem with a grilling session.
2. Record the domain language and important decisions.
3. Write the specification and system sketch.
4. Split the work into small dependency-aware tickets.
5. Give an agent one ticket at a time.
6. Review the diff against both the ticket and the specification.

This gives me a better balance between speed and control. Agents are useful for implementation and repetitive work, but the human developer must preserve the shared understanding of the system.
