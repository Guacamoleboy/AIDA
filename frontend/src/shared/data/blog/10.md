# Working together with agents.

Today was about **Collaborative Agentic Development**. The focus was on how several people and AI agents can work in the same development process without destroying the architecture or stepping on each other's changes.

I normally work alone on my AIDA project, so collaboration is not only about coordinating with another person. It is also about coordinating my own work with the agent. If I give an agent a vague task while I am changing the same files, I should not be surprised if the result becomes messy.

### A ticket is a contract

One of the most useful ideas today was that an agent ticket should work like a small contract. It should explain the goal, the allowed files, the files that must not be changed, the acceptance criteria and how the work should be verified.

For example, a ticket for customer search should not only say “add search”. It should explain the endpoint, whether the search is case-insensitive, what happens with an empty value and what the JSON response should look like. It should also tell the agent which controller, service, repository and test files it may touch.

I especially like having an explicit **out of scope** section. Agents are very good at finding opportunities to change more than I asked for. That might be helpful sometimes, but it can also make a small task turn into a general refactoring session.

### Branches and ownership

Branches are important when several people or agents work at the same time. Each task should have its own branch and a clear base branch. That makes it possible to review the work, compare the changes and throw them away if the agent misunderstood the task.

Code owners and branch protection can add harder rules around the process. A prompt telling an agent not to touch security files is a soft guardrail. A repository rule that requires review before those files can be merged is a hard guardrail.

That distinction matters to me. Instructions are useful, but they are not the same as technical enforcement. If something is genuinely important, the system should help enforce it.

### My own workflow

In my own project I already use an agent as an implementation helper. I do the architectural thinking and decide what the result should be, while the agent helps me search through the codebase and implement the repetitive parts.

The lesson made me realise that I should improve the way I hand work over. I should include the files I expect to change, the files that are out of scope, the tests I want to run and the point where the agent should stop and ask me a question.

I also need to review the result as if another developer had created it. “The agent said it was done” is not verification. I need to inspect the diff, run the relevant tests and make sure that no unrelated files were changed.

### The practical balance

There is a balance here. A ticket can become so detailed that writing the specification takes longer than doing the task. On the other hand, a short and unclear prompt can create much more work later.

My approach will be to use a small template for normal tasks and a more detailed specification for changes involving APIs, databases, security or multiple agents. The bigger the risk of side effects, the more explicit the contract should be.

Collaborative agentic development is therefore not just about putting more agents into a project. It is about creating a process where humans and agents can work independently while still respecting the same boundaries.
