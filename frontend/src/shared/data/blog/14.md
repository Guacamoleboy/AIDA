# How MCP could be used in my project

The AIDA lesson asks for a short reflection on how MCP could be used in a project. For Engestofte Gods, the clearest example is a future check of wedding date availability. ([AIDA MCP lesson](https://aida.kursusmaterialer.dk/14-MCP/))

### The project today

The current MVP has no MCP server and no live calendar integration. The date guidance is currently part of the system instructions and rubric. For example, the school-project rules describe the 2027 and 2028 demo assumptions, while the project specification says that real availability must be confirmed by Engestofte. The assistant therefore cannot look up a real booking calendar today. ([Project specification](../docs/projekt/02-projekt.md); [AI prompt and rubric flow](../docs/diagrammer/ai-prompt-flow.svg))

### A possible date-check tool

If Engestofte had an authoritative calendar that could be queried, I could expose a read-only MCP tool such as:

```text
check_wedding_date(date)
→ available | unavailable | unknown
```

When the customer gives a date, the model could choose this tool. The MCP server would validate the date, call a backend service or an existing REST endpoint, and return the result. OpenAI would then use that result to phrase its reply. A response of `unknown` would let the assistant ask Engestofte to confirm rather than guessing. An availability check would not reserve the date or create a booking.

```text
Customer gives date
        ↓
OpenAI chooses check_wedding_date
        ↓
MCP server → backend/calendar
        ↓
Availability result → OpenAI → customer
```

The rubric could tell the model when a date check is appropriate, but the rubric alone cannot perform the lookup. The tool must be implemented and made available to the OpenAI request. The model also does not get general access to Java classes: the MCP server exposes only the specific tools we choose. ([MCP Tools specification](https://modelcontextprotocol.io/specification/2025-06-18/server/tools); [OpenAI MCP documentation](https://developers.openai.com/api/docs/guides/tools-connectors-mcp))

### MCP and REST solve different parts

REST is a way for applications to communicate. MCP standardises how an AI client discovers and calls tools. An MCP tool could call an existing endpoint such as `POST /v1/checkdates`; the date logic and calendar could stay in the backend. Alternatively, an MCP server could call a backend service directly.

If this were the only tool and OpenAI were the only AI client, ordinary function calling might be simpler. MCP becomes more useful if the same date lookup should be available to several AI clients through the same tool interface. OpenAI's Responses API can connect to a remote MCP server and return the tool result to the model as part of the response flow. ([OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling); [OpenAI MCP documentation](https://developers.openai.com/api/docs/guides/tools-connectors-mcp))

### My conclusion

MCP could make date availability a real lookup instead of a prompt assumption, but only after Engestofte has a reliable calendar source and agrees how it should be used. I would begin with a read-only availability check, validate its inputs and result in the backend, and keep final confirmation with the Owner. MCP is a possible extension, not part of the current MVP.
